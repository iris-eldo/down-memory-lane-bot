# Down Memory Lane

A Slack bot that turns a text request into a photo of you as a kid — generated by an AI model trained specifically on your own face.

---

## What It Does

Post something like *"your 5-year-old self on a beach"* in Slack, and about 20-30 seconds later you get back a photo that actually looks like you at that age, in that scene — not a generic AI kid. No slash commands, no separate app. You just talk to it like a coworker, and it replies in the same thread.

The reason it looks like you specifically, and not just "a child," is that the underlying image model was fine-tuned ahead of time on 20 of your own reference photos. That one-time training step is what separates this from a generic "make me a kid photo" prompt — the model has actually learned your face and renders it into whatever scene you describe.

We tested this end-to-end with three prompts:

- "Your 2-year-old self in your house's backyard"
- "Your 5-year-old self on a beach"
- "Your 10-year-old self in a classroom"

All three came back as real, recognizable photos, posted directly in the requesting thread.

---

## How a Request Flows Through the System

1. You post a message in a channel the bot's been invited to.
2. Slack's Events API forwards that message to our server within about a second.
3. The server immediately replies — *"Generating: your 5-year-old self on a beach..."* — so the thread doesn't look stalled while the image renders.
4. The message text gets turned into a prompt (your description plus a trigger word the model was trained to recognize) and sent to Replicate, the hosted AI platform running our trained model.
5. Replicate generates the image and returns a public URL, typically in 10-30 seconds.
6. The server posts that image straight into the same Slack thread — no download/re-upload step, since Replicate already hosts it publicly.
7. If anything fails along the way (a bad request, a model error, a network issue), you get a clear in-thread error message instead of silence.

Nothing in this loop needs its own database. Slack handles messaging, Replicate handles the AI compute, and our server is the thin layer connecting the two — which keeps it simple to reason about and cheap to run.

---

## Training the Model (the one-time step behind all of this)

Before the bot can generate anything, it has to learn your face. This happens once, ahead of runtime, not per-request:

- 20 personal reference photos get bundled into a zip and uploaded to Replicate.
- Replicate fine-tunes a Flux image model, using `ostris/flux-dev-lora-trainer`, over 2,000 training steps. The output is a LoRA — a lightweight add-on to the base model that teaches it one specific face without retraining the whole thing from scratch.
- Training bakes in a unique trigger word (we used `IRISFACE`), which every future prompt includes. That word is what tells the model "use the face you learned," instead of generating a generic person.
- The result is a versioned model we can call from code any number of times going forward, without ever retraining — training is the expensive, slow step; every generation after that is fast and cheap by comparison.

## Design Choices Worth Knowing About

A few decisions in how this was built, and the reasoning behind each:

- **Reply before the image is ready.** Generation takes real time (10-30 seconds); an immediate acknowledgment keeps the thread from looking broken during that window.
- **Everything stays threaded.** If multiple people ask for different photos in the same channel at once, replies never get mixed up with each other.
- **The image URL gets posted directly, not re-uploaded.** Pointing Slack straight at Replicate's hosted image is faster and removes a failure point, compared to downloading and re-uploading a copy ourselves.
- **The bot ignores its own messages and edits.** A small filter, but it's what stops the bot from ever replying to itself in a loop.

## Implementation Details (for the technically curious)

This section goes a level deeper than the flow diagram above — the actual code structure, request/response shapes, and error handling.

**Stack:** Python, Flask (web server), Slack Bolt (Slack's official event-handling framework), the `replicate` Python client, `python-dotenv` for config. Single-file app (`app.py`), ~110 lines.

**The one endpoint that matters:**
```
POST /slack/events
```
This is registered with Slack as the app's Request URL under Event Subscriptions. Every event Slack sends — messages, in our case — arrives here as a signed HTTPS POST. Slack Bolt's `SlackRequestHandler` verifies the request signature (using the app's signing secret) before anything else runs, which is what stops random traffic from being able to trigger the bot.

**The event subscription itself** is scoped narrowly on purpose: only `message.channels` (messages posted to public channels the bot's a member of), backed by the `channels:history` and `chat:write` bot token scopes. Nothing broader is requested.

**Handler logic, roughly:**
```python
@bolt_app.event("message")
def handle_message(event, say, client, logger):
    if event.get("bot_id") or event.get("subtype"):
        return                      # ignore bot messages, edits, joins, etc.

    description = (event.get("text") or "").strip()
    channel = event["channel"]
    thread_ts = event.get("thread_ts", event["ts"])   # thread if replying, else start one

    say(text=f"Generating: _{description}_ ...", thread_ts=thread_ts)

    prompt = f"{TRIGGER_WORD}, {description}"
    output = replicate.run(REPLICATE_MODEL, input={"prompt": prompt})
    image_url = str(output[0] if isinstance(output, list) else output)

    client.chat_postMessage(
        channel=channel, thread_ts=thread_ts,
        blocks=[{"type": "image", "image_url": image_url, "alt_text": description}],
    )
```

A few things worth calling out in that logic:

- **`thread_ts` defaults to the triggering message's own timestamp** if it wasn't already a reply — meaning a fresh request starts its own thread, while replying inside an existing thread keeps the conversation contained there instead of spawning a new one.
- **`output` handling is defensive.** Different Replicate model versions return either a single URL/`FileOutput` object or a list of them depending on how the underlying model is packaged — casting with `str(output[0] if isinstance(output, list) else output)` handles both without needing to know which one in advance.
- **The whole Replicate call sits inside a try/except.** Anything that goes wrong — an invalid model version, a Replicate outage, a malformed prompt — gets caught, logged server-side via `logger.exception`, and turned into a plain-language in-thread reply rather than a silent failure or a Slack-side timeout.
- **`bot_id`/`subtype` filtering** is the one line standing between this working cleanly and the bot replying to its own "Generating..." message, spiraling into an infinite loop. Worth flagging because it's an easy thing to miss on a first pass.

**Config and secrets:** everything environment-specific (`SLACK_BOT_TOKEN`, `SLACK_SIGNING_SECRET`, `REPLICATE_API_TOKEN`, `REPLICATE_MODEL`, `TRIGGER_WORD`) is loaded from a `.env` file via `python-dotenv` at startup, with a `check_config()` guard that fails fast with a clear message if anything required is missing — rather than the app starting successfully and only breaking later on the first real request.

**Local dev networking:** the Flask app runs on `localhost:5002`, exposed publicly through an ngrok tunnel so Slack's servers (which only deliver events to public HTTPS URLs) can reach it. This is purely a development convenience — the app code itself has no dependency on ngrok and would run identically behind any real public host.

## Future Scope & Expansion

What's here is a working proof of concept, tested end-to-end with real prompts and real output. That's deliberately the smallest version that proves the idea — everything below is where it could go from here.

### Closing the gap to production

A few things separate this from something you'd hand to real users today, worth being upfront about:

- **The server runs locally right now, tunneled out via ngrok.** Moving to a permanently hosted endpoint (a small always-on server or serverless function) is a deployment change, not a redesign — the app code itself doesn't care where it's hosted.
- **It's built for one person's face.** Supporting multiple people means mapping each Slack user to their own trained model — a straightforward extension, just not built into this version.
- **No rate limiting yet.** Each generation costs a small amount on Replicate's usage-based pricing; production would want basic guardrails so nobody runs up an unexpected bill, accidentally or otherwise.
- **Secrets currently live in a local `.env` file.** Fine for development, but a real deployment should move API tokens into a proper secrets manager.

None of these are hard problems — they're the normal gap between "it works" and "it's live for real users."

### Where this could actually go

Beyond just hardening what exists, the core idea — a chat interface in front of a personally fine-tuned image model — opens up a few directions:

- **Team-wide rollout.** Once the per-user model mapping above exists, this stops being a personal demo and becomes something an entire workspace could use — anyone in Slack asking for a photo of themselves, a teammate, even a pet, each pulling from their own trained model.
- **Richer scene control.** Right now a prompt is just "trigger word + whatever you typed." Adding light prompt engineering — style presets ("cartoon," "vintage film," "watercolor"), mood, lighting, or era-specific cues — would let people get more consistent, higher-quality results without needing to know how to write a good AI prompt themselves.
- **Beyond Slack.** The bot logic doesn't actually know or care that it's talking to Slack specifically — the same core (prompt-building + Replicate call) could sit behind a Teams bot, a standalone web app, or an API other internal tools call into.
- **Self-serve model training.** Right now training a new face means someone manually zipping photos and kicking off a job on Replicate. A lightweight "upload your photos here" flow — even just a Slack command that accepts a batch of images and handles the rest — would remove the only manual step left in the whole system.
- **Smarter cost control.** Once usage moves beyond a handful of people, this is a natural spot for per-user or per-workspace usage caps, cached results for repeated prompts, and basic analytics on what people are actually generating — useful both for cost management and for understanding what feature to invest in next.

### Why it's worth building further

The interesting part isn't the novelty — it's that the whole loop (chat interface → personalized AI generation → instant delivery back where the conversation already is) is a pattern that generalizes well beyond "photo of me as a kid." The same shape — a fine-tuned model sitting behind a chat surface people already use every day — is the same underlying approach useful for personalized marketing assets, internal creative tooling, or any product where "generate something that looks like *this specific thing*" matters more than generic AI output. This project is a small, concrete proof that the pattern works end-to-end, cheaply, with tools that already exist off the shelf.
